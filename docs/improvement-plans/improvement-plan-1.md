## 结论

首份方案只做两件事：把报名、IM、文件和入口身份修到单实例可证明正确；在稳定契约上补一条可演示的校园社团业务闭环。性能优化和多实例高可用分别等待容量证据和部署需求后另立方案。

首期报名采用 MySQL 条件更新和唯一键，不在本方案引入 Redis Stream/报名 Outbox。首期 IM 采用数据库事务提交后 ACK，不以 Kafka 接收作为消息成功边界。文件任务和业务引用需要持久化，因为只存 Redis 无法满足刷新、重启和撤权验收。

## 目标、非目标与不变量

| 类型 | 内容 | 完成判据 |
|---|---|---|
| 目标 G1 | 可信身份、可配置 ID 和正确的 WS 连接替换 | 伪造头无效；双节点 ID 样本无重复；旧连接关闭不影响新连接 |
| 目标 G2 | 报名单库事务正确性 | 不超卖、不重复、事务失败不丢名额，响应与数据库终态一致 |
| 目标 G3 | 消息提交后 ACK、稳定幂等与 seq 补拉 | ACK 后可补拉；重试返回原 ID；跨页无遗漏；非成员无权访问 |
| 目标 G4 | 可恢复 Multipart 和业务引用授权 | Redis 丢失可续传；重复合并同结果；撤权后不可下载 |
| 目标 G5 | 三账号完成最小业务流程 | 创建/审核/入社/群聊/活动报名/文件/移除撤权 E2E 通过 |
| 非目标 | 容量调优、K8s、数据库/中间件副本、分库分表、完整观测平台、AI 新功能 | 保持现状且不回归；达到后续方案门槛再评估 |

跨工作包不变量：数据库是报名和消息终态来源；对象默认私有；64 位 ID 在 JSON 中使用字符串；权限以服务端用户和业务关系为准；任何“已完成”都必须有当前运行证据。

## 设计决策与取舍

| 决策 | 选择 | 原因与代价 |
|---|---|---|
| 报名成功边界 | MySQL 事务：唯一订单 + 条件扣库存，提交后返回成功 | 当前规模下最短的正确路径；牺牲 Redis 秒杀峰值吞吐。容量证明确有需要后再引入异步受理 |
| IM 成功边界 | 单库事务保存 clientMsgId/msgId/seq，提交后 ACK | 可直接满足重试和补拉；Kafka 只做已提交消息的副作用，后续多实例再评估 Outbox |
| 消息游标 | 每会话单调 seq | 比 msgId/createTime 混合游标可验证；需要新增列、唯一索引和历史回填 |
| 文件模型 | upload_task、file_object、file_reference 分离 | 支持同内容不同用户任务、恢复和撤权；需要新增表与旧 file_meta 兼容迁移 |
| 跨服务成员同步 | 可重试领域事件或补偿任务，并提供对账 | 不用同步 Feign 冒充分布式事务；需要事件幂等和重放入口 |
| 发布方式 | P1–P4 分包验收，P5 在契约冻结后实施 | 降低同时修改后端、迁移和前端造成的返工；整体演示时间晚于单项修复 |

## 接口与数据迁移

| 工作包 | 兼容方式 | 发布顺序 | 数据核对 | 回退点 |
|---|---|---|---|---|
| W1 | nodeId 新配置提供单实例默认值；身份头若经测试无漏洞则无需改实现 | 网关与 IM 配置先发布，再启动第二实例 | ID 重复样本、在线 route token 与本地映射一致 | 回到单实例；保留新配置，已证实的安全修复不回退 |
| W2 | 读取兼容旧 PROCESSING；新写只产生明确终态 | 先迁移/核对旧订单，再发布服务和前端 | `total_stock - available_stock` 与成功订单数按活动核对 | 停写、备份、回滚应用；禁止 Redis 反灌 DB |
| W3 | 新增列/索引；cursor 接口保留旧入口一版并标弃用 | 加列 → 回填 seq → 加唯一索引 → 双读 → 切客户端 | 每会话 seq 连续性、clientMsgId 冲突、消息总数 | 回滚客户端/应用，保留新增列，不逆向删数据 |
| W4 | 新表旁路旧 file_meta；旧文件只读，归属不明不公开 | 建表 → 新上传写新表 → 迁移可确认记录 → 切读取 | 任务、对象、引用计数及对象摘要 | 关闭新上传，保留表和对象；应用退回旧只读路径 |
| W5 | 新入口受 feature flag 控制；事件有 eventId 幂等 | 后端/消费者 → 数据准备 → 前端逐入口启用 | club_member 与会话成员、文件引用权限对账 | 关闭 flag 和写 API，保留可重放事件并运行对账 |

所有数据库变更使用版本化 migration，不直接只改 `docker/mysql/init.sql`。初始化 SQL 与 migration 最终都要能得到相同结构。删除旧列、旧表和旧对象不属于本方案的首次发布；稳定运行一个版本后另开清理任务。

## 验收矩阵与证据格式

| 场景 | 输入 / 故障点 | 必须观察到的结果 | 证据 |
|---|---|---|---|
| 身份伪造 | 有效 token + 冲突 X-User-* | 下游只看到 token claims | 网关测试与实际请求日志 |
| 报名并发 | 名额 N，请求数 > N，含同用户重试 | 成功不超过 N；每用户一单；DB 库存一致 | 自动化测试、SQL 对账、并发参数 |
| 报名回滚 | 条件扣减后插入/提交失败 | 库存与订单同时回滚 | 故障注入日志和 SQL 快照 |
| IM 重试 | DB 提交前断开、提交后 ACK 丢失 | 前者无成功 ACK；后者重试返回同 msgId/seq | WS 脚本、消息行和 ACK |
| IM 分页 | 单会话消息超过两页 | seq 单调，无遗漏/重复，nextCursor 正确 | 请求响应与集合校验 |
| Multipart | URL 过期、Redis 清空、重复 complete | 可重签并只补缺片；完成结果幂等 | MinIO 请求、对象摘要、任务状态 |
| 权限撤销 | 用户被移出社团后重试聊天/下载 | 发送、补拉、下载均拒绝 | API/WS 响应与权限对账 |
| 完整流程 | 用户 A、用户 B、管理员 | tasks.md P5 的全流程无手工改库完成 | 浏览器 E2E、API 报告、数据终态 |

每份证据记录：基线 commit/工作区、操作系统、JDK/Maven/Node/pnpm/Docker 和镜像版本、命令、测试数据规模、通过/失败/跳过数、失败日志位置。Mock 单测不能替代真实 Kafka/MinIO/数据库故障场景。

## 风险与暂缓项

| 风险 / 暂缓项 | 触发条件 | 处理 |
|---|---|---|
| 并行修改冲突 | 多个 Agent 修改同一业务文件或 schema | 按 W1–W4 划分所有权；合并前重新读取 diff，不覆盖未知改动 |
| 历史数据无法确定归属 | file_meta 没有可靠 club/reference 信息 | 保持私有并输出人工处理清单，不推断为公开 |
| seq 回填冲突或长锁 | 真实消息量大于预估 | 分批回填、先建非唯一辅助索引，在影子库计时后发布 |
| MinIO SDK 兼容问题 | 公共 API 无法完成签名/Complete/ListParts | 先做最小技术验证；必要时升级到固定版本并补兼容测试，不继续反射内部实现 |
| 异步报名 | 单库在固定资源下达不到已确认目标 | 完成 W2 后以 O04 基线另立容量方案，不在本方案临时叠加 Stream/Outbox |
| 多实例、K8s、副本 | 没有 SLO/RTO/RPO 或维护资源 | 暂缓至 Improvement Plan 3，不作为 W1–W6 完成条件 |
