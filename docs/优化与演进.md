# 项目优化与演进

> 当前实施入口是 [tasks.md](../tasks.md)，首份可执行方案是 [Improvement Plan 1](improvement-plans/improvement-plan-1.md)。未达到启动条件的项目保持候选，不进入当前待办。

## 分层原则

项目按四类问题分别规划：

1. **正确性修复**：已有行为可能丢消息、丢名额、无法恢复或越权，优先处理。
2. **业务闭环**：补当前缺失的创建、管理和页面，让现有模块能完成一条真实流程。
3. **容量与性能**：必须先有同条件基线和明确瓶颈，不能凭架构想象提前优化。
4. **多实例与高可用**：必须先有单实例正确性、部署需求、SLO/RTO/RPO 和维护预算。

Improvement Plan 1 只覆盖第 1、2 类以及其必需的测试基线。第 3、4 类分别作为未来 Plan 2、Plan 3 候选；AI 能力作为 Plan 4 候选。这样业务闭环、性能和多实例不会混成一次无法独立验收的发布。

## O03–O07：容量与性能候选（未来 Plan 2）

统一启动条件：Plan 1 的 P6 已通过；测试数据、并发模型、硬件、JVM、连接池、限流和依赖版本固定；同一瓶颈至少可重复三次。未满足时只允许补测量，不实施架构性优化。

| ID | 候选方向 | 要先回答的问题 | 比较指标 | 采用触发条件 |
|---|---|---|---|---|
| O03 | Gateway Redis 与事件循环 | 黑名单 Redis 访问是否阻塞 WebFlux 线程？延迟来自哪里？ | 吞吐、P95/P99、事件循环阻塞、超时率 | Redis 延迟对入口 P99/错误率形成已测主瓶颈 |
| O04 | 报名峰值 | 单库条件更新的上限是否低于真实活动需求？热点在 DB、连接池还是入口限流？ | 成功受理吞吐、锁/池等待、不变量错误数 | 真实峰值需求超过安全容量后，才评估异步 202、Redis Stream/Outbox |
| O05 | IM 群聊与慢客户端 | 每消息查询次数、节点扇出和慢连接队列的实际开销是多少？ | 发送至 ACK/接收 P99、SQL 次数、队列长度、断线补拉量 | 目标群规模下延迟或资源越过已确认 SLO |
| O06 | 查询与连接池 | 哪些 SQL 扫描/等待最多？现有 `(conversation_id,seq)` 等索引是否足够？ | EXPLAIN ANALYZE、扫描行、锁等待、池等待 | 有慢查询样本，且索引/批量方案有同条件收益证据 |
| O07 | 上传交互与清理 | 浏览器摘要、弱网分片和孤立对象的主要失败来源是什么？ | 主线程阻塞、重传字节、成功率、孤立对象体积 | 真实大文件/弱网场景未达到产品目标 |

Plan 2 若启动，每次只选择已证明的瓶颈。报告必须区分入口请求、业务成功和最终完成，并附修改前后相同条件结果；功能与权限回归是性能结论成立的前提。

## O10：多实例与高可用候选（未来 Plan 3）

Plan 3 只有同时满足以下条件才创建为待实施方案：

- Plan 1 P6 通过，单实例下报名、消息和文件不变量已验证；
- 明确为何需要至少两个业务实例，或明确可接受的停机时间；
- 写出 SLO、RTO、RPO、预估连接/请求/数据量和维护者；
- 有 MySQL、Redis、Kafka、MinIO 副本及备份恢复所需资源预算。

| 子项 | Plan 1 只做的兼容基础 | Plan 3 才实施和验证的内容 |
|---|---|---|
| ID | 显式且不重复的 node/worker 配置 | 自动租约、冲突检测、时钟回拨策略 |
| WS | sessionId 条件删除、带 session token 的在线值 | TTL/续租、节点摘流、跨节点路由、滚动升级、节点失联恢复 |
| 消费与任务 | 业务幂等键、可重放入口 | Consumer rebalance、Outbox 并发认领、恢复任务互斥 |
| 限流 | 单实例安全默认值 | 用户/活动维度全局限流和共享出口校准 |
| 数据服务 | 单实例备份/恢复步骤 | 副本拓扑、故障切换、脑裂防护、实际 RTO/RPO 演练 |

K8s、分库分表和完整日志集群不是默认目标。只有实例管理或容量问题达到可记录阈值，并且运维收益大于维护成本时才纳入 Plan 3。

## O11–O12：AI 候选（未来 Plan 4）

统一启动条件：业务权限和文件/消息引用稳定；存在明确用户入口、固定评估集、费用预算和数据保留策略。

| ID | 候选方向 | 前置条件 | 验收 |
|---|---|---|---|
| O11 | 对话与只读工具 | 用户/会话隔离、工具端点鉴权、超时和预算限制完成 | 会话连续性、跨用户隔离、工具成功率/P95、token 与费用报告 |
| O12 | 可追溯问答与摘要 | 检索按社团权限过滤，消息拥有稳定 seq 和引用 | 固定 30–50 题；正确率、引用可追溯率、撤权、延迟和成本 |

实时名额通过业务 API 查询，不从向量索引猜测。写操作工具展示参数并取得用户确认后执行。

## 新方案的最低信息

新 Improvement Plan 必须包含：基线 commit、问题证据、目标与非目标、可独立工作包、依赖、接口/数据迁移、回滚、验证输入和规模估算假设。缺少任一项时保持“候选”，不得写成“待实施”。

已修复的现状要从候选问题描述中删除或改为完成证据。历史“已完成”若不能在当前环境复现，状态降为待验证。
